## 3. P0 — блокирует живой пилот (исправить первым)

### D-01. В режиме `pilot` вход через браузер по HTTP отклоняется (`403 Origin mismatch`)

- **Где:** `platform/server.js:1601–1608` (проверка Origin в обработчике `/api/*`), источник `server.js:30` (`const DEMO = process.env.APP_MODE !== 'pilot'`).
- **Код:** `if (req.method === 'POST' && req.headers.origin && req.headers.origin !== (!DEMO ? 'https://' : 'http://') + req.headers.host) → 403`.
- **Симптом:** как только `APP_MODE=pilot`, любой POST из браузера по `http://` (локально, в школьной сети, на тестовом VPS без TLS) получает `403 Origin mismatch`. Форма входа «молчит»: ученик видит непонятную ошибку, учитель — тоже.
- **Воспроизведено:**
  ```
  APP_MODE=pilot AI_PROVIDER=openai OPENAI_API_KEY=test DATA_DIR=/tmp/pilotdata PORT=3101 node platform/server.js
  curl -i -X POST localhost:3101/api/login -H 'Origin: http://localhost:3101' -d '...'  → 403
  curl -i -X POST localhost:3101/api/login                          -d '...'  → 200
  ```
- **Почему важно:** владелец собирается тестировать сначала локально/у знакомых, то есть **без HTTPS**. Это первый же барьер пилота.
- **Что сделать:**
  1. Ввести `PUBLIC_ORIGIN` (например `https://course.example.com`) — при заданном значении разрешать только его (как сейчас, fail-closed).
  2. Если `PUBLIC_ORIGIN` не задан — сравнивать с фактической схемой: `X-Forwarded-Proto` (за доверенным прокси) или `req.socket.encrypted ? 'https' : 'http'` + `Host`.
  3. При несовпадении возвращать не только 403, но и понятный текст (`Origin mismatch: expected …`), чтобы это не выглядело как «сервер сломался».
  4. Никогда не разрешать `null`/`*`/произвольный хост.
- **Критерий приёмки:** новый тест: `pilot` + `Origin: http://localhost:<port>` → `200`; `pilot` + `PUBLIC_ORIGIN=https://x` + `Origin: http://y` → `403`; без `Origin` → `200` (curl/скрипты не ломаются).

### D-02. Cookie сессии помечается `Secure` по режиму, а не по фактическому HTTPS

- **Где:** `platform/server.js:146`.
- **Код:** `'session=' + token + '; HttpOnly; SameSite=Strict; Path=/' + (!DEMO ? '; Secure' : '')`.
- **Симптом:** в `pilot` по HTTP браузер отбрасывает cookie. Сейчас вход «случайно» продолжает работать, потому что клиент дублирует токен в `localStorage` и шлёт `Authorization: Bearer` (`app.js:23`, `teacher.js:12`), но это не решение: cookie — единственный механизм для переходов `/preview/...`, прямых ссылок и (в будущем) отключения Bearer.
- **Почему важно:** хрупкая аутентификация + расхождение «документация говорит HTTPS, реальность HTTP».
- **Что сделать:** ставить `Secure` только при фактическом HTTPS (`X-Forwarded-Proto: https` или TLS-сокет) либо явным флагом `COOKIE_SECURE=true|false`. Добавить `Path=/; SameSite=Strict; HttpOnly` (уже есть) и, при желании, `Max-Age` = `SESSION_TTL_HOURS`.
- **Критерий приёмки:** тест: `pilot` + HTTP → в `Set-Cookie` нет `Secure`; `X-Forwarded-Proto: https` → `Secure` есть; cookie-вход (без `Authorization`) проходит на `/api/me`.

### D-03. Лимит запросов считается по IP — в классе все ученики делят один бюджет

- **Где:** `platform/server.js:1460–1469` (`throttle`), вызов `server.js:1608–1609`.
- **Код:** `const id = (req.socket.remoteAddress || '') + key;` + лимиты `20/мин` на `/api/login`, `120/мин` на остальные маршруты.
- **Симптом:** 10–15 учеников за одним NAT/школьным Wi-Fi делят 20 логинов в минуту и 120 запросов в минуту **на маршрут**. Урок начинается с одновременного входа класса → часть детей получает `429 Too many requests`, и после этого любая повторная попытка входа (ученик переспрашивает пароль) только ухудшает ситуацию.
- **Почему важно:** это ровно тот сценарий, ради которого делается пилот («небольшая группа»).
- **Что сделать:**
  1. Для авторизованных запросов ключ = `session.token` (или `studentId`), а не IP.
  2. Для `/api/login` — отдельный, более щедрый лимит (например, 60/мин на IP) + счётчик неудачных попыток **на конкретного ученика** (защита от перебора PIN), а не общий.
  3. Оставить глобальный «предохранитель» на IP с высоким порогом (например, 600/мин), чтобы не потерять защиту от флуда.
  4. Убедиться, что очистка словаря `rates` не течёт (сейчас чистка есть — `server.js:1444`; сохранить).
- **Критерий приёмки:** тест: 15 разных сессий с одного `127.0.0.1` делают по 20 запросов → все `200`; и тест, что 200 неудачных логинов одного ученика всё равно блокируются.

### D-04. «Живой» AI-путь ни разу не проверялся, а `/api/health` рапортует `ok: true` при неверном ключе/модели

- **Где:** `platform/ai-provider.js:47–88` (текст), `:89–137` (изображения), `platform/server.js:1590–1596` (`/api/health`).
- **Симптом:** в `pilot` с ключом, у которого нет доступа к `gpt-6-luna`/`gpt-image-2.5-sunburst`, `/api/health` отвечает `ok: true`; ошибка появляется только на первом запросе ученика — и приходит как `500 «Operation failed. Your saved work is unchanged»`. Диагностировать в классе невозможно.
- **Почему важно:** это единственный «включатель» пилота; цена ошибки — сорванный урок.
- **Что сделать:**
  1. Добавить `npm run check:live` (или `npm run smoke:live`) — **отдельная команда**, не в CI: один минимальный текстовый запрос и, по флагу, одна картинка 1024×1024; печатать модель, статус, `usage`/токены и оценку стоимости.
  2. В `ai-provider.js` различать классы ошибок провайдера и отдавать их наружу с кодом: `401/403` → «ключ/доступ», `404 model_not_found` → «модель недоступна аккаунту», `429` → «лимит провайдера», `5xx` → «сервис недоступен». Ученику — дружелюбный текст, в лог — технический.
  3. `/api/health` в `pilot` дополнить полем `liveChecked: true|false` + `lastError` (без ключей и промптов), чтобы учитель видел состояние.
  4. Задокументировать в `docs/API_SOURCE.md`, что имена моделей проверены по актуальной документации, и указать дату проверки.
- **Критерий приёмки:** тест с подменой `fetch`: `404 model_not_found` → ответ `сущ. 502/503` с текстом про модель, **не** `500`; и `/api/health` содержит `liveChecked`.

## 4. P1 — до первого живого урока и до деплоя

### D-05. Mock-черновик хобби не проходит собственный гейт → `500` вместо понятного отказа

- **Где:** `platform/ai-provider.js:8–18` (`mock`), `:48–53` (проверка и `throw`), вызовы `server.js:250`, `:275`, `:299` (`handlePrompt`).
- **Симптом (воспроизведено):** промпт с коротким `Context:` (`Context: I have skated.`) для поля `hobby-text-1` возвращает `HTTP 500` и общий текст «Operation failed…». Причина: `mock` для хобби даёт `12 слов + контекст` = 14 < порога 15 → `checkText` не проходит → `throw`. Для `about-me` шаблон 30 слов, поэтому падает только при почти пустом контексте.
- **Вторая часть проблемы:** mock-черновик хобби содержит Present Perfect только если ученик сам написал его в строке `Context:`; правила требуют PP и в финальном тексте хобби (`SYSTEM_INVARIANTS`, L2). Значит даже при длинном контексте без PP ученик получает отказ по `grammar` — тоже `500`.
- **Третья часть:** то же происходит в live-режиме после одного repair-повтора (`ai-provider.js:86`) — ученик получает `500`, хотя его промпт и ввод в порядке.
- **Почему важно:** mock — это официальный режим для репетиции и для проверки интерфейса; 500 в нём маскирует реальные проблемы и пугает ученика. Для живого режима `500` — ложная тревога «сломался сервер».
- **Что сделать:**
  1. Сделать mock **детерминированно валидным**: достраивать черновик до требований поля (минимум слов + Present Perfect, взятый из `Context:` или безопасная формулировка), без случайности; для `about-me` держать запас ≥ 45 слов даже при пустом контексте.
  2. Не бросать `500` на «продуктовую» ошибку: возвращать `200 {ok:false, errors:[{rule, hint}]}` или `422` с подсказкой «перепиши Context подробнее / добавь Present Perfect», чтобы ученик мог исправить.
  3. Сохранить принцип «нет скрытой подмены»: если live не смог — честный отказ, но **без** 500.
  4. Не «смягчать» гейты и не менять правила уроков — правится генератор и обработка ошибок.
- **Критерий приёмки:** тест по всем AI-полям L2 (`about-me`, `hobby-text-1..3`) с контекстом из одного Present Perfect-предложения: mock-черновик проходит `checkText` для каждого поля; и тест, что при имитации невалидного ответа live-провайдера возвращается `4xx` с `errors[]`, а не `500`.

### D-06. Коррекция поля у ученика сделана через два `window.prompt()` с потерей данных

- **Где:** `platform/public/app.js:318–325`.
- **Код:** `var reason=prompt('Why are you correcting this field?'); if(!reason)return; var text=prompt(…, fstate.value||'');`
- **Симптомы:**
  - два модальных окна подряд; при отмене второго введённая причина **теряется** (в журнал ничего не попадает, но и не сохраняется);
  - править 40–60 слов в однострочном поле на планшете невозможно;
  - для изображений нужно вручную ввести «Image version number», для темы — «1 или 2», без списка и без подсказки;
  - ошибки ввода (`checkText`) показываются после закрытия окон, без возможности исправить текст.
- **Почему важно:** это путь, которым пользуется ребёнок 10–14 лет без учителя рядом.
- **Что сделать:** inline-форма внутри карточки поля (паттерн в проекте уже есть — `renderPickPanel` в `app.js:1644`):
  1. `<textarea>` с текущим значением, заполненным заранее;
  2. отдельное поле причины (обязательное);
  3. для `ai-image-*` — `<select>` существующих версий (`iterations[].version` + миниатюра), для `theme-picker` — `<select>` из `option1/option2` с названиями пресетов;
  4. кнопки `Save correction` / `Cancel`; `Cancel` ничего не меняет и ничего не теряет;
  5. ошибки `errors[]` показывать внутри формы, форма остаётся открытой;
  6. `aria-label`/`label for` на полях.
- **Критерий приёмки:** ручная проверка в браузере по чек-листу (ниже) + отсутствие `prompt(` в `app.js` (`grep`).

### D-07. Учитель вводит технический `field.id` по памяти

### D-08. Параметры изображений передаются неявно — риск перерасхода и расхождения с документацией

Лимиты не ослаблять.
- **Критерий приёмки:** тест с подменой `fetch` фиксирует наличие `output_format`, `n`, `quality` в теле запроса изображения.

### D-09. Готовность L1 (бумажный урок) нигде не фиксируется, а `unlock L2` её не проверяет

- **Где:** гейт `server.js:1080–1106` (`handleUnlockLesson`) — проверяется только `isComplete(prev)`; для L1 кода нет вовсе (`grep -i l1 platform/server.js` → пусто).
- **Симптом:** по `docs/SYSTEM_INVARIANTS.md` и `Lesson_1.md` учитель подтверждает L1 вручную (карточки, соглашение, mind map, журнал), но система об этом не знает: `unlockedLessons` по умолчанию `[2]`, то есть L2 доступен сразу. Если в классе 12 детей, проверить «все сдали бумагу» и не забыть — организационно сложно.
- **Что сделать (минимально):** чекбокс `L1 paper work checked` в строке ученика в консоли учителя + поле `progress.l1Ready = {ts}`; при первом `unlock` L2 без него — предупреждение (не жёсткий блок, чтобы не сорвать урок), с записью в журнал учителя. Это не меняет методику, только фиксирует факт.
- **Критерий приёмки:** тест: `unlock` L2 без `l1Ready` → `200` + `warning`; с `l1Ready` → без предупреждения; значение сохраняется после перезапуска.

### D-10. `npm run backup` / `restore` падают стеком вместо подсказки

- **Где:** `package.json` (`"backup": "node tools/backup.js backup"`), `tools/backup.js:5–12`.
- **Симптом (воспроизведено):** `npm run backup` без аргумента печатает stack trace (`Usage…` бросается как исключение). Пользователь, читающий README, решит, что backup сломан. При этом `docs/DEPLOY_RUNBOOK.md` описывает вызов с абсолютным путём.
- **Что сделать:** печатать `usage` и `exit 1` без stack trace; в `README`/`DEPLOY_RUNBOOK` дать рабочую форму `npm run backup -- /абсолютный/путь`; добавить `npm run restore -- /путь`. Проверить, что backup **не** попадает в `DATA_DIR` (проверка есть) и что restore отказывает в непустое назначение (проверка есть — сохранить).
- **Критерий приёмки:** тест: `node tools/backup.js` без аргументов → код возврата 1 и одна строка `Usage…`, без `Error:`. Round-trip backup→restore на временном `DATA_DIR` (тест уже есть — расширить на CLI).

### D-11. CI не проверяет ни вход, ни `pilot`, ни mock-валидность

- **Симптом:** CI состоит из `build/check/test`. Тесты работают только в `APP_MODE=demo` (по умолчанию) и не покрывают: `Origin`/cookie/`Secure` (D-01, D-02), лимиты (D-03), provisioning `pilot` без `classes.json`, mock-валидность (D-05), CLI backup (D-10), L1-гейт (D-09). Именно поэтому все дефекты выше «прожили» до аудита.
- **Что сделать:** добавить тест-файл `tests/pilot.test.js` (запуск сервера в `pilot` с временным `DATA_DIR`, проверка D-01/D-02/D-03) и `tests/provider.test.js` (D-05, D-08). Добавить в CI шаг `npm run smoke` после `npm start` в фоне (или отдельный скрипт `npm run ci`), чтобы проверялся живой HTTP-слой.
- **Критерий приёмки:** `npm test` включает новые файлы; падение любого из P0-тестов ломает CI.

### D-12. Дрейф документации и кода: PowerShell-пайплайн, которого уже нет

- **Критерий приёмки:** `grep -rn "ps1\|PowerShell\|powershell"` по репозиторию (кроме `docs/history`) пуст; `npm run check` зелёный.

### D-13. Мёртвый публичный эндпоинт `/api/save-edit`

- **Где:** `platform/server.js:438–455`, маршрут `:1519`. Работает только для legacy-типа `ai-cycle`, который не используется ни одним полем конфигов; клиент (`app.js`) и тесты его не вызывают.

При удалении — удалить и `handleSaveEdit`, и запись в `studentHandlers`, и `'ai-cycle'` из карты `types`.

### D-14. Противоречия в отчётах и отсутствие `.nvmrc`

- **Критерий приёмки:** `npm ci` на Node 22 без `EBADENGINE`; в репозитории нет двух разных чисел «групп тестов».

## 8. Обязательные новые тесты

1. `pilot`: вход по HTTP из «браузера» (`Origin`) → `200`; чужой `Origin` при заданном `PUBLIC_ORIGIN` → `403`.
2. `Set-Cookie` без `Secure` по HTTP и с `Secure` при `X-Forwarded-Proto: https`; вход по одной cookie (без Bearer).
3. 15 сессий с одного IP по 20 запросов → без `429`; перебор PIN одного ученика — блокируется.
4. Mock: для `about-me` и `hobby-text-1..3` черновик при минимальном корректном промпте проходит `checkText` (тест падает на текущем коде).
5. `ai-provider`: `404 model_not_found`, `429`, `timeout`, отказ модели → `4xx` с `errors[]`, не `500`; бюджет не «съедается» неуспешной попыткой ученика.
6. Тело запроса изображения содержит `output_format: 'png'`, `n: 1`, `quality`.
7. `backup.js` без аргументов → код 1, одна строка usage, без stack trace; round-trip на временном `DATA_DIR`.
8. `unlock` L2 без `l1Ready` → предупреждение в ответе; с `l1Ready` — без предупреждения; после перезапуска сервера флаг на месте.
9. Регресс: полный L2–L5 (существующий тест) остаётся зелёным после всех правок.

git clone https://github.com/serg-ai-vn/AI_English_Course.git

 "students":[{"id":"s1","name":"S1","pin":"5678"}]}]}
JSON
