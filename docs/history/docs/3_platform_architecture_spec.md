## Главный принцип (без изменений)

Не сто отдельных аккаунтов детей в сторонних сервисах, а одна тонкая обёртка поверх ваших собственных API-ключей. Дети работают внутри вашего приложения; оно ходит в модели от одного аккаунта. Это по-прежнему решает регистрацию (логин от учителя, не детский email), оплату (опт по API вместо 10 подписок) и контроль (весь трафик через ваш backend).

Дальше — то, что изменилось по итогам разбора.

## 1. Сборка сайта: свой шаблон, не чужой конструктор

**Пересмотрено.** Сторонние no-code инструменты (конструкторы сайтов, внешние билдеры) — лишний груз именно для вашего случая, и вот почему: они спроектированы для взрослых пользователей с личными аккаунтами, а не для контролируемого классного окружения с логированием и фильтрами. Чтобы встроить туда свой Prompt Journal и систему контроля, пришлось бы городить обвязку вокруг чужого продукта с непрозрачной структурой ответа — то есть ровно те костыли, которых вы разумно хотите избежать.

**Рабочая схема** — та же архитектура, что вы уже проверили на цифровом сотруднике: **детерминированная логика снаружи, ИИ — генератор контента внутри.**

- Вы заранее собираете HTML/CSS-шаблон сайта с чётко определёнными "слотами": заголовок, блок "обо мне", карточки увлечений, слоты под картинки.
- LLM генерирует не сайт целиком, а **контент для конкретного слота**: текст абзаца, промпт для картинки.
- Backend просто подставляет сгенерированный контент в нужный слот шаблона.

Никакого стороннего конструктора не нужно вообще. Плюсы: полный контроль над тем, что логируется (структура ответа — ваша, а не чужого API), одна точка интеграции (свой шаблон + LLM API + API генерации изображений), и это ровно тот паттерн, который вы уже умеете строить.

## 1.1 Визуальная тема: CSS-переменные + ограниченный набор пресетов

**Контент отличается у всех и так — но без этого слоя стиль (цвета, шрифты) был бы одинаковым у всех 10 сайтов.** Решение той же природы, что и остальная архитектура: не открытый доступ к CSS, а управляемый, ограниченный набор.

- Шаблон строится на **CSS custom properties** (`--background`, `--accent-primary`, `--font-heading` и так далее) — не захардкоженных значениях.
- Существует **фиксированный набор из 6 пресетов** (см. источник "Site Theme Presets") — не свободный выбор цвета. Каждый пресет — просто набор значений для этих переменных.
- Ребёнок описывает желаемое настроение по-английски через формулу промпта **R.C.T.F.** (Role/Context/Task/Format: mood-слово в Format) → система сопоставляет первое mood-слово с пресетом → применяется live preview → второй вариант обязателен (смена mood → возможно другой пресет, тот же пресет = мягкое предупреждение) → ребёнок выбирает и фиксирует обоснование в журнале (comparative + дизайн-слово). Промпт жёстко ограничен словарём из 8 mood-слов, никогда — сырым CSS.
- Тот же цикл "предложил → оценил → сравнил → выбрал", что уже работает для текста и картинок — новый домен, не новый паттерн взаимодействия.

**Разделение по уровню персонализации** (см. источник "Site Theme Presets v2"): три приёма движения по странице (плавное появление блоков, чередование появления слева/справа, посимвольное проявление текста) — **одинаковые у всех**, часть шаблона, не выбор ребёнка. Только "Particle Assemble" — эффект рассыпания/сборки аватара — персонален, и то лишь по цвету частиц (берётся из выбранного пресета). Это сознательное разделение: даёт ощущение современного, "вау"-инструмента всем одинаково, а инженерные усилия на реальную персонализацию концентрирует в одном месте, а не размазывает на пять независимых анимационных систем.

**Почему именно 6, не произвольный выбор**: ограниченный набор гарантирует, что результат будет выглядеть цельно независимо от чувства цвета у конкретного 12-летнего — и держит логику сопоставления простой (небольшой словарь ключевых слов → пресет, не полноценная модель принятия решений).

## 2. Система контроля процесса (гейтинг) — разбор механики

Вот здесь стоит чётко разделить два разных по природе механизма, которые вы описали одним словом — они технически разные и решаются по-разному.

### A. Детерминированный гейтинг — это код, не ИИ

Требования вроде "минимум 3 итерации", "каждый следующий промпт длиннее предыдущего", "использованы 2 слова из сегодняшнего списка лексики" — всё это проверяется простым кодом: подсчёт слов, сверка со списком, счётчик итераций, сравнение с предыдущей версией. **Вызов ИИ для этого не нужен.**

Почему это важно сделать именно кодом, а не ИИ-проверкой: код работает мгновенно, бесплатно и на 100% предсказуемо — не может "поплыть" и один раз пропустить то, что должен был отклонить. Для пилота, где всё должно быть отточено до мелочей (ваши слова — "не золотуха", а чётко выверенный результат), это ключевое свойство: одна и та же ошибка ребёнка всегда получает одну и ту же реакцию системы, и это можно протестировать заранее, до живого урока.

**Подсказки при отказе** — тоже не требуют отдельного вызова ИИ. Это таблица соответствия "какая проверка не прошла → какая подсказка показывается", написанная вами заранее. Например: не прошла проверка длины — *"Try adding a word about color, mood, or setting"*; не прошла проверка лексики — *"Try using one of today's words: [список]"*. Не готовая фраза для копирования, а указание, в какую сторону думать — ровно то, что вы и хотели. Это набор правил в коде, а не нейросеть, отвечающая каждый раз по-разному.

### B. Срежиссированные учебные моменты — это отдельная, контролируемая сущность

Для общих обучающих демонстраций (например, "Hallucination Hunt" из методички) — здесь оправдано заранее подготовить гарантированный пример, а не надеяться, что живая модель ошибётся именно сегодня и именно педагогически удачно. Это заранее написанный, проверенный кусок контента (промпт + заведомо известный результат), который вы показываете всей группе — а не тайное вмешательство в модель.

**Личную работу каждого ребёнка трогать не нужно.** Живая модель и так выдаёт неидеальные результаты (обобщённые фразы, странности на картинках) — этого естественного несовершенства достаточно, чтобы гейтинг из пункта A сработал и заставил ребёнка итерировать. Специально портить именно его результат смысла нет: гейтинг уже работает на любом реальном выводе модели, а срежиссированный пример нужен только там, где сценарий требует гарантированного результата на глазах у всей группы одновременно.

## 3. Аватары вместо фото — и что происходит с данными после защиты

**Во время курса** (на вашей системе): никаких настоящих фото, только псевдонимы. Вместо загрузки фото — промпт-описание себя ("двенадцатилетний, кудрявые волосы, в очках, любит футбол") → ИИ рисует стилизованный аватар. Это не потеря "вау-эффекта", а его источник в другой форме: увидеть, как ИИ рисует "тебя, но как аниме-персонажа" по твоему же описанию, для этого возраста часто более эффектно, чем просто загруженное фото — и это уже само по себе демонстрация возможностей ИИ, а не компромисс ради комплаенса.

**После защиты** — семье передаётся **полный экспорт**: файлы или доступ на их собственный хостинг (например, их личный Google Sites), а не продолжающийся доступ на редактирование на вашем сервере. Это принципиально: после экспорта именно семья решает, добавлять ли настоящее имя и фото — и с этого момента это уже не имеет отношения ни к центру, ни к вам технически. Публикация в конце Занятия 5 должна быть буквально шагом экспорта/передачи, а не "вот ссылка, которая вечно живёт на нашем сервере".

## 3.1 Бумажный этап (Занятие 1) — как он попадает в общую систему

> **Статус (06.08): НЕ реализовано — это будущий кусок.** Текущая платформа стартует с L2; ниже — целевая схема.

Занятие 1 без компьютеров не оставляет цифрового следа само по себе. Чтобы Prompt Journal не имел дыры в самом начале, бумажные материалы (mind map, лист "AI or Not AI", подписанное соглашение) фотографируются и прикрепляются к записи ученика вручную — простая функция загрузки фото в консоли учителя, привязанная к конкретному ученику и Занятию 1.

**Условие по сценарию**: "цифровая маска" вводится в блоке Practice — до того, как дети переходят к бумажной работе в Wrap-up. Значит, если явно попросить писать на бумаге псевдоним, а не настоящее имя, начиная с этого момента — фотографии из Wrap-up естественно останутся без личных данных.

**Подписанное соглашение — отдельный случай.** Если для отчётности центру нужна подпись настоящим именем — держите этот лист отдельно, бумажным архивом у учителя, не фотографируйте в общую систему. Если такой необходимости нет — подписывайте тем же классным псевдонимом, что и everywhere else; сопоставление псевдоним↔имя остаётся у центра отдельно от AI-системы, как и остальные персональные данные по нашей схеме.

**Для MVP пилота**: просто хранить фото как есть, без распознавания рукописного текста. Автоматический разбор почерка — это уже следующий этап, не то, что нужно для первых 10 детей.

**Разблокировка Занятия 2**: сама загрузка этих фото учителем в консоль — и есть триггер. В момент загрузки статус ученика переключается на "Lesson 1 complete", и цифровое рабочее место Занятия 2 становится доступным по его логину. На первое время это просто ручное действие учителя (кнопка "Unlock Lesson 2" рядом с загруженным фото), не автоматическая проверка содержимого — тело фото не анализируется, доверие к тому, что учитель сверился с бумажным чек-листом перед загрузкой.

## 4. Из чего состоит система (обновлённый список компонентов)

**Индивидуальное рабочее место ученика.** Важное уточнение по итогам разбора: реальная группа 10 человек и занятие 60–90 минут физически не позволяют работать через один общий проектор с очередью — на это не хватит времени, и вы это верно почувствовали. Значит, у каждого ребёнка — своё устройство (планшет) и свой логин. Это не избыточное усложнение MVP, а фактический необходимый минимум при таком размере группы и времени.

**Backend с двумя слоями:**
- Слой генерации: вызовы к LLM (текст) и к API генерации изображений.
- Слой валидации: набор из 5–8 простых правил-проверок (описаны в п. 2A) плюс таблица подсказок к ним.

**Консоль учителя** — **построена (31.07-05.08)**: таблица учеников со статусами (complete/working/not-started/needsAttention), чипы AI-полей с прогрессом итераций, раскрываемый Prompt Journal по урокам (`?lesson=N`), lastActivity, действия Unlock Lesson / Build site / Publish (L5), авто-refresh. Простая таблица, не аналитика реального времени — как и задумано.

**БД-логгер** — как и раньше, каждый запрос и ответ пишется в базу; из этого автоматически собирается Prompt Journal.

**Авторизация** — код класса + имя + PIN, выдаёт учитель.

## 5. Как это связано с педагогикой — теперь два механизма, не один

**Prompt Journal собирается автоматически из логов** — как и раньше: раз все запросы идут через backend, журнал "было → стало" из методички формируется сам, без ручного заполнения, и не может быть подделан задним числом.

**Гейтинг из п. 2A — это не просто фиксация процесса, а его принудительное обеспечение.** Раньше архитектура только записывала, что произошло. Теперь она активно не пропускает ребёнка дальше, пока не выполнено требование рубрики (минимум итераций, использование целевой лексики) — то есть требования методички не полагаются на добрую волю ребёнка или бдительность учителя, а встроены в сам инструмент. Это даёт именно ту предсказуемость результата за 5 занятий, о которой вы говорите: система физически не даст группе "проскочить" минимальный уровень проработки, независимо от того, насколько внимателен учитель в моменте.

## 6. Что строить для пилота — реалистичный объём на 1–2 месяца

Вы правы, что здесь нет ничего сверхсложного для вашего уровня — ниже конкретный список того, что реально нужно собрать, без завышения и без занижения:

- Один HTML/CSS-шаблон сайта со слотами (собирается один раз).
- 5–8 правил-валидаторов + таблица подсказок к ним (п. 2A) — простой код, не ИИ.
- Два API-интеграции: генерация текста, генерация изображений.
- Индивидуальные рабочие места учеников (простая веб-страница с логином по коду класса).
- Простая консоль учителя (таблица, не дашборд реального времени).
- Лёгкая база данных для логов и Prompt Journal.
- Заранее подготовленный контент для срежиссированных моментов (п. 2B) — 1–2 таких на весь курс.

**Инженерный совет на будущее, чтобы не переписывать всё заново**: списки лексики, правила валидации и слоты шаблона стоит с самого начала хранить как настраиваемые данные (конфигурацию), а не зашивать в код под конкретное занятие. Тогда переход от бесплатного 5-занятийного пилота к платному 10-занятийному модулю (о котором вы говорили как о следующей ступени) — это добавление контента и правил, а не пересборка системы с нуля.

## 7. Данные детей — техническая реализация (уточнено под новую логику фото)

- Во внешний API для генерации текста/изображений уходит только псевдоним и содержание промпта — без имени, возраста, адреса, реального фото.
- Технический запрет на загрузку файлов-фото в интерфейсе — только текстовое описание для аватара. Это отсутствие самой кнопки, не вопрос дисциплины.
- В договоре с центром: центр — контроллер данных (у него отношения с родителями и их согласие), ваша платформа — обработчик.
- Момент экспорта (п. 3) — это чёткая граница ответственности: до него данные обезличены и под вашим контролем, после — переданы семье и вне зоны вашей технической ответственности.

Этот документ по-прежнему работает вместе с методичкой (что происходит в классе) и бизнес-брифом (почему это стоит делать и в какой рамке) — но теперь архитектура не просто описывает инструмент, а показывает, как инструмент сам обеспечивает выполнение методики, а не полагается на то, что учитель или ребёнок сделают всё правильно по доброй воле.
