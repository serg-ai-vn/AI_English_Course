## 0. Краткое резюме (вердикт)

1. **Это не два равных варианта одного и того же.** Подход 1 — это *план и «память проекта»*, подход 2 — *исполненный и проверенный результат*. Подход 2 эти дефекты исправил и закрыл тестами.
2. **Для стадии 1 (минимально рабочая, но стабильная версия, которую вы будете менять) нужно брать за основу подход 2.** Он единственный, который сегодня вообще запускается, проходит автоматические проверки и имеет восстановимую историю Git.
3. **Подход 1 не нужно выбрасывать.** Он содержит то, что подход 2 при сжатии потерял: матрицу связей «6 слоёв кода» с типичными ловушками, подробное описание платформы «как есть» с разделом «известные дыры», и пошаговый (а не декларативный) GitHub-гайд. Это стоит перенести в подход 2 в компактном виде.
4. **Подход 2 перегружен процессом** для одного человека: 16 пунктов аудита, три отчётных документа, 45 КБ архивного лога в активной папке, отдельный протокол независимой приёмки. Для стадии 1 это дороже, чем польза. Процесс надо сократить, **не трогая** тесты, CI, разделение данных и secrets.
5. **«Всё отлично» — нет.** Найдено 6 пунктов P0/P1, которые всплывут при первом же тесте на живых людях (главный: в режиме `pilot` браузер не сможет войти по обычному HTTP — это проверено экспериментально). Полный список в разделе 9.

## 3. Подход 1: сильное и слабое

### 3.1 Сильное

1. **Матрица межфайловых зависимостей** — самая ценная часть. Перечисляет конкретные ловушки: `groupsFor()` в `app.js` решает, появится ли поле на экране; префиксы `id` (`hobby-text`, `reflection-`) используются валидатором; `data-slot` в `index.html` должен совпадать с ключами `runExport()`; `about-me` — единственный слот, где создаётся `<p>`.
2. **«Impact Check»** — правило «сначала предупреди, потом меняй»: перед правкой урока проверить 6 слоёв (config → validate → server → app → teacher → шаблон/экспорт). Это ровно то, что снижает риск «поправили одно правило — отвалился гейт в другом уроке».
3. **`PLATFORM.md` с разделом «известные дыры»** — честная фиксация ограничений (полезно перед пилотом).
4. **Пошаговый GitHub-гайд** с командами, тегом baseline и порядком задач — для не-инженера это практичнее, чем декларативные правила.
5. **Методическая полнота:** планы уроков со скриптами учителя, таймингом, рубрикой, карточками, соглашением, пресетами.

### 3.2 Слабое (подтверждено кодом)

1. **`motion.js` не парсится.** В baseline-коммите `node --check motion.js` даёт `SyntaxError: Unexpected token '}'` (лишняя строка `el.appendChild(frag);`). Следствие: у всех собранных сайтов учеников мертвы анимации. Это дефект ровно того артефакта, который подход 1 готовил к загрузке.
2. **Экспорт сайта работает только на Windows.** В baseline сборка вызывает `powershell.exe tools/export-site.ps1` и `sample-particles.ps1`. На Linux/VPS это не заработает вообще, на Windows зависит от политики выполнения скриптов.
3. **Открытая выдача файлов.** `/preview/` в baseline не требует авторизации и отдаёт любой файл внутри корня трека — то есть `.env` с ключом и `platform/data/sessions.json` с живыми токенами (проверяется по коду baseline). Это критическая уязвимость, а не косметика.
4. **Нет автоматических проверок.** Ни тестов, ни CI. `smoke`-скрипт печатает статус и **не возвращает код ошибки**, поэтому «4/4 зелёных» ничего не гарантирует.
5. **Опасный Git-процесс:** `git merge task-01-... && git push origin main` напрямую в `main`, без PR, без приёмки, без прогонов.
6. **Дрейф внутри собственной документации:** в матрице указаны номера строк (`server.js` 1311–1488 и т. п.), которые на момент аудита уже не совпадают с файлом (1 816 строк). Это классическая болезнь «подробных» документов.
7. **Планы по AI устарели:** `TASK-03` предполагает `gpt-4o-mini` + `dall-e-3`, тогда как подход 2 перешёл на Responses API + images API. Если бы пошли по подходу 1 буквально, заложили бы вчерашнюю модель.
8. **Дублирование источников истины:** `PLAN.md`, `4_implementation_roadmap.md`, `3_platform_architecture_spec.md` и `PLATFORM.md` в значительной степени пересказывают друг друга (89 КБ на одну и ту же тему).

- Сборка перенесена с PowerShell на Node + `sharp` (кроссплатформенно, без самописного PNG-декодера).

- CI (Node 24: build + check + test), Dockerfile + compose, `.env.example`, `fixtures/` отдельно от runtime-данных.
- Git: baseline-коммит с тегом → ветка → draft PR → независимая приёмка → merge → тег `v0.6.0-local`. Проверяемо и воспроизводимо.

### 4.2 Сильное

1. Продукт **работает** и проверяется одной командой.
2. Данные и секреты отделены от исходников; есть backup/restore с контрольными суммами.
3. Инструктивный слой сжат в 4 раза (44,9 КБ → 11,2 КБ) и стал навигационным (`CONTEXT_MAP`), а не «читай всё».
4. Исторические документы не удалены, а помечены баннером `HISTORICAL SNAPSHOT` — хороший компромисс против потери знаний.
5. Отчётность честная: `NOT_RUN` не выдаётся за `PASS`.

### 4.3 Слабое

1. **Перегруз процесса.** 16 пунктов аудита (`AUD-01…16`), три отчётных документа, отдельный протокол независимой приёмки для проекта, который ещё ни разу не видел ученика. Это стоимость без отдачи на стадии 1.
2. **Дрейф кода и комментариев.** В `server.js` (строки ~1116–1170) сборка всё ещё описана как «запускает два PowerShell-скрипта, `export-site.ps1`» — при том что код давно вызывает `builder.exportSite`. Те же отсылки остались в `particles.js`, `tools/fill-slots.js`, `slots-config.json` (`"sampler": "tools/sample-particles.ps1"`), а сами `.ps1` лежат в `tools/`. То есть подход 2 лучше контролирует документацию и хуже — комментарии в коде.
3. **Внутренние противоречия в отчётах:** `ACCEPTANCE` — «6/6 групп», `IMPLEMENTATION_STATUS` — «5/5 групп», `VERIFICATION_REPORT` — «5 групп»; фактически 6 тестов. Мелочь, но подрывает доверие к отчётам как к источнику истины.
4. **Код остался монолитом:** `server.js` 1 816 строк, `app.js` 1 840 строк, `validate.js` 590. Для MVP приемлемо, но именно интерфейс (1 840 строк) не покрыт автоматическими тестами — любое изменение механики урока проверяется вручную.
5. **Потеряны операционные детали** из подхода 1: матрица 6 слоёв сжата до одной строки, «известные дыры» платформы, карта `nextStep`-переходов, пошаговый GitHub-гайд.
6. **Заявленная приватность не соответствует факту:** репозиторий публичный, а три документа утверждают «приватный». Персональных данных в репозитории нет (проверено), но расхождение надо устранить — либо привести доки к факту, либо закрыть репозиторий.

## 7. Что вернуть из подхода 1 в подход 2 (дешёво и с высокой отдачей)

1. **Компактную матрицу 6 слоёв** (15–20 строк вместо 3 КБ), без номеров строк:
   `config/lesson-N.json → validate.js → server.js (nextStep, runExport, buildStudentView) → public/app.js (groupsFor, renderRules) → public/teacher.js → index.html + fill-slots.js`.
   С тремя ловушками: `groupsFor` не покажет новое поле; префиксы `id` завязаны на валидатор; `data-slot` обязан совпадать с ключами экспорта; `about-me` — единственный `<p>`-слот.
2. **Раздел «Известные ограничения»** в `PLATFORM.md` (перенести 5–7 пунктов из архивного `PLATFORM.md`, обновив факты).
3. **Карту `nextStep`-переходов** как одну таблицу (A1-prompt → A1-eval → A2-prompt → A2-eval → A3-publish → done; B1-prompt → B1-fork → done; I1-prompt → I1-eval → … → pick → accept; T1-prompt → T2 → choose → justify). Это то, что агент чаще всего ломает.
4. **Пошаговый «первый запуск»** (10 команд + ожидаемый вывод) — либо в `README`, либо в `DEPLOY_RUNBOOK`. Новичку-помощнику это нужнее, чем политика из 6 пунктов.

## 10. Какой подход придерживаться (прямой ответ)

**База — подход 2. Процесс — сократить. Память — забрать из подхода 1.**

Конкретно:

1. **Источник истины — GitHub, ветка `main`.** Google Drive оставить как архив/приёмник отчётов. Не редактировать проект в двух местах: сейчас Drive содержит `package.json` 0.5.0 и код baseline, то есть это уже не «вторая реализация», а исторический снимок. Его стоит переименовать в `ARCHIVE_baseline_2026-10-29` и больше не трогать.
2. **Ветка = одна задача = один PR.** Уже работает, оставить. Merge только при зелёном CI; тег на каждый значимый milestone (сейчас `v0.6.0-local` — правильно).
3. **Три документа вместо девяти.** Активными оставить: `AGENTS.md` (правила), `SESSION.md` (≤ 100 строк, где мы сейчас), `docs/SYSTEM_INVARIANTS.md` (что нельзя ломать) + `tasks/00-BACKLOG.md` (что дальше). `ACCEPTANCE`, `VERIFICATION_REPORT`, `IMPLEMENTATION_STATUS`, `SESSION_HISTORY_ARCHIVE` — в `docs/history/`; статус — одной таблицей в `BACKLOG`.
4. **Никаких новых «протоколов приёмки» на стадии 1.** Достаточно: тесты + CI + ручная браузерная проверка по чек-листу из 6 пунктов, записанная в PR одной строкой. Независимую приёмку вернуть перед первым платным/массовым запуском.
5. **Оставить безусловно:** тесты, CI, разделение `DATA_DIR`/`fixtures`, `.env.example`, baseline-тег, backup/restore, запрет `reset` по умолчанию, отчёт `PASS/FAIL/NOT_RUN` без выдуманных «4/4».
6. **Отложить безусловно:** Docker/VPS (до реального ключа и первой группы), Supabase, ИИ-тьютор, конструктор курсов, аналитику.
7. **Вернуть из подхода 1:** матрицу 6 слоёв, карту `nextStep`, раздел «известные ограничения», один пошаговый сценарий первого запуска.

**Формула для стадии 1:** «маленькая документация + автоматические проверки + одна проверенная ветка + жёсткая дисциплина данных». Всё остальное — после первых наблюдений.

## 12. Definition of Done для «минимально рабочей и стабильной» стадии 1

1. `npm ci && npm run build && npm run check && npm test` — зелёные на чистом клоне.
2. Вход ученика и учителя работает и в локальной сети, и на HTTPS-домене.
3. Полный маршрут L2–L5 проходится без ручных правок данных; после перезапуска сервера прогресс на месте.
4. Реальный AI отвечает, отклоняет некорректный ответ и не превышает бюджет; отказ не «съедает» попытку ученика.
5. Учитель собирает сайт, публикует и отдаёт ссылку; ссылка открывается на телефоне.
6. Backup/restore проверены, время восстановления известно.
7. Ни одного реального имени/фото/PIN в Git; `DATA_DIR` вне репозитория.
8. Изменение любого правила урока проходит по матрице 6 слоёв и подтверждается тестом.
9. Документация: `AGENTS` + `SESSION` + `INVARIANTS` + `BACKLOG` актуальны; всё остальное — история.
10. Один человек со стороны (не вы) проходит L2 по инструкции без ваших подсказок.
