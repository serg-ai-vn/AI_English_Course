## 4. Визуальная спецификация новой темы

Рабочее название: **Classroom Light**, идентификатор `classroom-light`. Старая тема: **Night Lab**, идентификатор `night-lab`.

| Роль | Значение из образца | Применение в платформе |
|---|---|---|
| Фон страницы | `#fefcf7` | Тёплая кремовая основа |
| Поверхность | `#ffffff` | Формы, основные карточки, таблицы |
| Основной текст | `#141414` | Заголовки, задания, содержимое полей |
| Второстепенный текст | `#2b2b2b`, `#555555` | Навигация, подписи, пояснения |
| Спокойная рамка | `#e6d8b5` | Разделение поверхностей |
| Главный акцент | `#FFB703`, градиент `#FFE47A → #FFB703` | Главное действие или текущий учебный фокус |
| Дополнительный акцент | `#FB8500` | Полоса примера, небольшие детали |
| Информационный акцент | `#219EBC`, `#8ECAE6` | Подсказки и поддерживающие элементы |
| Успех | `#2e9e5b`, фон `#eafaf0` | Сохранено, завершено, успешно |
| Ошибка | `#e23b3b`, фон `#fff2f2` | Ошибки и отклонённые действия |
| Поддерживающие карточки | `#fff9e6`, `#eef9fc` | Правила, примеры, объяснения |

Это базовая палитра, а не разрешение использовать любые её сочетания. На жёлтых/оранжевых кнопках нужен тёмный текст. Для небольших зелёных/красных/бирюзовых подписей при необходимости использовать более тёмные производные и записать точные значения с проверкой контраста. Текст ошибки должен читаться и без цветового различия. Бежевую декоративную рамку не считать достаточной границей поля ввода, если она не различима.

Типографика светлой темы: Poppins 400/500/600/700, запасной стек `system-ui, -apple-system, 'Segoe UI', sans-serif`. Заголовки 600–700, основной текст 400–500, действия 600. Начальный ориентир для рабочей формы: основной текст 16–18 px, подписи 14–16 px, заголовки карточек 20–24 px, главный заголовок `clamp(26px, 3.4vw, 36px)`, line-height 1.45–1.6. Размеры 21–26 px из слайдов не переносить на всю плотную таблицу учителя. Финальные значения выбирать по реальной вёрстке и фиксировать в дизайн-документе.

Геометрия: карточки с радиусами примерно 16–24 px, отдельные главные блоки до 28 px; ясные отступы и видимые границы. Чёрная рамка 2–3 px и жёсткая нижняя тень 4–7 px допустимы для главного фокуса/основного действия. Не обводить так каждый элемент таблицы. Не навязывать платформе размеры слайда 980×585 или фиксированную пропорцию 85/15.

Иерархия:

- В текущей рабочей области выделено главное доступное действие; навигация и служебные кнопки спокойнее.
- Правило, пользовательский ввод, AI-ответ, журнал и обратная связь визуально различаются, но их содержание и порядок остаются прежними.
- Отсутствуют тёмные полупрозрачные панели, светлый текст на светлом фоне и малозаметные градиентные заголовки в светлой теме.
- Небольшой фоновый декор допустим, если не мешает чтению. Звёздный фон Night Lab в светлой теме убрать или заменить спокойным.
- Текстовые подписи действий сохранять. Правило презентации «служебные кнопки только иконками» не распространять на формы платформы.
- Состояния normal/hover/focus/active/disabled, загрузки, ошибки, предупреждения, selected/done/locked проектировать явно. Disabled не должен выглядеть как доступное действие.

## 5. Архитектура двух тем

Рекомендуемая реализация без копирования приложения:

1. Оставить один набор HTML, обработчиков, CSS-геометрии и компонентов.
2. В `platform.css` выделить семантические токены для поверхностей, текста, рамок, действий, статусов, фокуса, теней, шрифтов и декора. Существующие названия можно связать с ними, если это уменьшает риск.
3. Для Night Lab сохранить текущие цвета, шрифты, фон, тени и визуальный характер. Базовые значения в `:root` допускаются как прежний безопасный fallback; явный `html[data-ui-theme="night-lab"]` должен работать на всех страницах.
4. Значения Classroom Light и действительно необходимые компонентные переопределения ограничить `html[data-ui-theme="classroom-light"]`. Не использовать глобальные замены `background`, `color`, `font-family` для всех потомков или массовые `!important`.
5. Добавить отдельный `platform/public/ui-theme.js`. Он отвечает только за выбор и применение темы оболочки; не импортирует логику уроков.
6. На трёх HTML-страницах явно задать стартовую светлую тему и подключить один и тот же небольшой bootstrap в `<head>` до основного stylesheet/первой отрисовки. Избежать вспышки неверной темы при сохранённом Night Lab. Обработчик темы не должен ждать API или восстановления прогресса.
7. Добавить `ui-theme.js` в **точный** allowlist `platform/server.js`. Новые отдельные CSS допустимы только с такой же явной регистрацией; рекомендуемый минимальный вариант оставляет стили в `platform.css`. Не открывать весь каталог или произвольные пути.

Контракт настройки:

- Атрибут оболочки: `data-ui-theme`; он не заменяет и не переиспользует `SITE_DATA.theme`, `progress.theme`, учебные preset IDs или `data-theme` ученического шаблона.
- Отдельный ключ localStorage: `aiEnglishCourse.uiTheme.v1`.
- Допустимы только `classroom-light` и `night-lab`. Отсутствующее/неизвестное значение → Classroom Light. Системная тёмная тема ОС сама по себе не переопределяет этот выбор.
- Чтение и запись localStorage — через try/catch. При запрете хранилища платформа работает с темой по умолчанию; ошибку записи нельзя превращать в сбой входа/урока.
- Выбор относится к браузеру и origin, не к ученику/классу. Он сохраняется при переходах login/workspace/teacher, перезагрузке и выходе из аккаунта. Не очищать остальной localStorage и не переписывать token/role/studentName.
- Предусмотреть маленький общий интерфейс, например `window.PlatformTheme.setTheme(id)`, для будущего переключателя. Применение меняет только атрибут/стили и preference; не перерисовывает карточки, не вызывает reload, не отправляет запросы на запись и не меняет focus/scroll/введённый текст.
- Документировать возврат: в консоли браузера `window.PlatformTheme.setTheme('night-lab')`; обратно — `window.PlatformTheme.setTheme('classroom-light')`. Если имя API изменено, обновить документацию и тесты. Этот способ работает уже в первом выпуске, до видимого переключателя.

Шрифты: сохранить Inter/Space Grotesk для Night Lab и подключить Poppins для светлой темы, с `display=swap` и fallback. Не делать загрузку шрифта условием работы интерфейса. Проверить отсутствие сети к Google Fonts; для текущего выпуска внешняя загрузка соответствует существующей практике проекта. Самостоятельное размещение шрифтов — только при обоснованной необходимости, с лицензией, MIME и точным allowlist; не расширять эту задачу автоматически.

Подготовить описание дизайна, отчёт и draft PR. После независимой приёмки конкретного SHA и решения владельца о публикации/слиянии выполнить процедуру раздела 11. Не считать новый внешний вид принятым только по тестам: владелец должен увидеть основные экраны и возврат к Night Lab.

## 9. Матрица проверок

Все проверки данных выполняются на отдельных синтетических fixtures в временном DATA_DIR. Не запускать seed/reset на пользовательских данных, не пользоваться сервером владельца на 3000, не завершать чужие Node-процессы. За остановку тестового сервера отвечает тот, кто его создал.

| Проверка | Что должно быть подтверждено |
|---|---|
| `npm run check` | Синтаксис, JSON и контракт полей |
| `npm test` | Все существующие Node-тесты; статус каждого падения разобран |
| `npm run build` | Сборка синтетического demo-export; исходный шаблон и результат не зависят от UI-темы |
| `npm run smoke:isolated` | Изолированный HTTP smoke; расширить проверку на новую статику и три страницы |
| `npm run test:ui` | Существующие сценарии коррекций плюс новые проверки тем; основной workflow прогнать в обеих темах с независимыми fixtures |
| Статика и доступ | Новый JS/CSS отдаются 200 с правильным MIME; произвольные/private пути по-прежнему закрыты |
| Настройка темы | По умолчанию светлая; сохранённая тёмная; неверное/отсутствующее значение; storage read/write throws; переходы между страницами и reload |
| Применение без потери состояния | Переключить тему в незавершённой форме/коррекции; значения, фокус, прокрутка, раскрытый журнал и состояние кнопок сохраняются; нет API-записей; progress/revision равны до/после |
| Отсутствие конфликта L4 | Цветовые образцы, демонстрационные шрифты, обе опции, выбранный preset и экспорт одинаковы при смене UI-темы |
| Пользовательский путь | На mock-fixtures пройти ввод → генерация → оценка → правка → завершение; L3/L4 выборы; L5; учительские unlock/build/preview/publish/export и коррекция с отзывом старых ссылок |
| Ошибки и ожидание | Ошибка валидации, загрузка, отказ/таймаут провайдера, пустые и завершённые состояния читаемы и не выглядят как успех |
| Совместимость | Открыть ранее сохранённый синтетический профиль pilot-1, продолжить работу без сброса; тема не меняет профиль |

Для экспорта использовать один и тот же фиксированный синтетический input до/после; сравнить содержимое, а при детерминированной сборке — SHA256. Проверка существующих API-тестов не заменяет браузерный маршрут. Если часть сценария покрыта только API, так и написать.

Визуальная проверка обеих тем:

- Desktop 1280×900 (существующая конфигурация), 1366×768; tablet 768×1024; mobile 390×844 и минимальная ширина 320 px.
- Увеличение 200%, длинные подсказки/имена/тексты, пустое поле и заполненное поле, длинный журнал. Нет обрезанных действий, перекрытий и горизонтальной прокрутки страницы; отдельный скролл таблицы допустим, если понятен.
- Tab/Shift+Tab/Enter/Space, видимый focus, логичный порядок, подписи формы, контраст. Целевые пороги приёмки: 4.5:1 для обычного текста, 3:1 для крупного текста и значимых границ/индикаторов. Записать измеренные пары, особенно ошибки и подписи на цветных фонах.
- Загрузка Poppins и fallback при блокировке Google Fonts; проверить вьетнамские диакритические знаки/кириллицу там, где они реально встречаются. Проверка fallback-шрифтов не является проверкой полной офлайн-работы сервера.
- `prefers-reduced-motion`: новая тема не добавляет обязательную анимацию; все действия доступны без неё.
- До/после Night Lab сравнивать при одинаковых viewport, данных и загруженных шрифтах. Новую тему смотреть вручную, а не только по pixel-diff.
- Проверить отсутствие ошибок JS и 404 новых ассетов. Сохранить обезличенные снимки ключевых состояний и ссылку на них в отчёте/PR.

Эмуляция viewport не подтверждает работу на физическом планшете или проекторе. Реальные устройства, реальные платные AI-запросы и VPS/HTTPS отмечать отдельно как PASS/FAIL/BLOCKED/NOT_RUN. Их историческая непроверенность не должна исчезать из BACKLOG после смены темы.

## 11. GitHub, локальная копия и исключения

Требование «нет расхождений» означает одинаковый финальный commit и дерево **отслеживаемых файлов** локального Main и GitHub main. Локальные DATA_DIR, зависимости, runtime-сборки и папка черновиков остаются только локальными; их наличие не является рассинхронизацией исходников.

1. Работать в ветке. До commit проверить `git diff`, `git diff --check`, список новых файлов и `git diff --cached --name-status`. Добавлять явный список нужных файлов, не выполнять слепой `git add .`.
2. Папка `Создание презы первого урока` остаётся вне Main. В `.gitignore` Main добавить защитное правило `Создание презы первого урока/`, чтобы случайно скопированная внутрь папка тоже игнорировалась. Правило не удаляет уже отслеживаемые файлы — проверить `git ls-files` отдельно. Сами образцы не коммитить, не прикладывать к публичному PR и не публиковать через runtime.
3. Убедиться, что новые коммиты не содержат .env, ключей, профилей, пользовательских экспортов, backups и приватных скриншотов. Снимки тестов — только синтетические.
4. Отправить ветку, создать draft PR по шаблону проекта. Описать результат, границы, проверки, риски, возврат к Night Lab; приложить сравнимые изображения. Не пушить изменения напрямую в main.
5. Получить независимую приёмку именно финального SHA согласно AGENTS.md. При изменениях после review повторить затронутые проверки и приёмку нового SHA. Слияние — после согласованного владельцем этапа выпуска; если агенту дано только исполнение/проверка, оставить draft PR и отчёт.
6. Перед merge проверить свежесть base, CI и отсутствие конфликтов. При изменении main объединить изменения в рабочей ветке и перепроверить; не перезаписывать чужие коммиты.
7. После merge в Main при чистом рабочем дереве выполнить `git fetch origin`, перейти на main и `git pull --ff-only origin main`. Если fast-forward невозможен, сохранить изменения и разобраться; не использовать `reset --hard`, force push или принудительный clean.
8. Подтвердить `git rev-parse HEAD` = `git rev-parse origin/main` = SHA из свежего `git ls-remote origin refs/heads/main`. `git diff --exit-code HEAD origin/main` и `git status --porcelain=v1` должны быть пустыми. Повторно проверить отсутствие черновиков среди отслеживаемых файлов.
9. Записать ссылку PR, merge SHA и доказательство readback в итоговый ответ. Доказательство финальной синхронизации можно оставить в ответе/PR, чтобы его запись новым локальным коммитом не создала очередное расхождение. Если нужен новый репозиторный отчёт после merge, провести его отдельным согласованным PR и повторить синхронизацию.

Планирование само по себе не публикует этот пакет: временное локальное отличие документации ожидаемо и должно быть явно обозначено. В конце выпуска проверяется и код, и документация. `origin/main` без свежего fetch/remote readback не доказывает соответствие GitHub.

## 12. Возврат и восстановление

**Возврат к старому виду:** применить `night-lab` штатным API темы. Это предпочтительный способ, если не нравится дизайн: не меняются код уроков и данные. Возврат по умолчанию для всех браузеров — отдельная маленькая правка default, с учётом сохранённых пользовательских preferences.

**Отмена выпуска при регрессии:** использовать точный merge/squash SHA этого изменения и `git revert` в отдельной ветке с PR; для merge-коммита проверить правильный parent. Не выдавать универсальную команду с непроверенным SHA. После исправления/отката повторить необходимые проверки и синхронизацию.

Миграции данных здесь нет, поэтому откат оформления не должен восстанавливать старую базу поверх новой ученической работы. При отдельном обновлении работающего сервера действовать по DEPLOY_RUNBOOK с резервной копией в разрешённом локальном месте; не делать backup/restore частью обычного переключения темы.
